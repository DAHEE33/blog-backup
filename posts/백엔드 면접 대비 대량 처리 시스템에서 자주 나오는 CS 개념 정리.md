<p>대량 발송 시스템이나 예약/결제 시스템처럼 요청이 순간적으로 몰리는 서비스에서는 단순히 코드를 빠르게 작성하는 것보다, 요청을 어떻게 분산하고 실패를 어떻게 처리할지 설계하는 것이 중요하다.<br />이번 글에서는 동기/비동기 처리, 메시지 큐, DLQ, 멱등성, 멀티스레드, DB 커넥션 풀 개념을 대량 발송 시스템 관점에서 정리한다.</p>
<h2>1. 동기 처리와 비동기 처리</h2>
<p>동기 처리는 요청한 작업이 끝날 때까지 호출한 쪽이 기다리는 방식이다.</p>
<p>예를 들어 이메일 발송을 동기 방식으로 처리하면 다음과 같다.</p>
<pre class="excel"><code>사용자 요청
&rarr; DB 저장
&rarr; 이메일 발송 API 호출
&rarr; 이메일 발송 완료
&rarr; 사용자에게 응답
</code></pre>
<p>이 구조에서는 이메일 발송 API가 느리면 사용자 응답도 같이 늦어진다.<br />외부 업체 API가 일시적으로 느려지거나 장애가 발생하면 전체 요청 흐름이 영향을 받는다.</p>
<p>반면 비동기 처리는 오래 걸리는 작업을 현재 흐름에서 분리하는 방식이다.</p>
<pre class="excel"><code>사용자 요청
&rarr; DB 저장
&rarr; 이메일 발송 요청을 Kafka/MQ에 저장
&rarr; 사용자에게 먼저 응답
&rarr; 이메일 발송은 뒤에서 처리
</code></pre>
<p>비동기 처리를 사용하면 사용자 요청 흐름과 실제 발송 처리를 분리할 수 있다.<br />이메일 발송, 문자 발송, 파일 생성, 외부 API 연계처럼 시간이 오래 걸리거나 실패 가능성이 있는 작업에 적합하다.</p>
<h2>2. 메시지 큐를 사용하는 이유</h2>
<p>Kafka, RabbitMQ, IBM MQ, AWS SQS 같은 메시지 큐는 요청을 바로 처리하지 않고 중간에 쌓아두는 역할을 한다.</p>
<p>대량 이메일 발송을 예로 들면, 요청이 한 번에 10만 건 들어왔다고 해서 외부 발송 업체 API에 10만 건을 동시에 보내면 문제가 생길 수 있다.<br />내 서버는 요청을 보낼 수 있어도, 외부 업체가 그만큼 처리하지 못하면 timeout이나 실패가 늘어날 수 있다.</p>
<p>메시지 큐를 사용하면 다음과 같은 구조를 만들 수 있다.</p>
<pre class=""><code>발송 요청
&rarr; Kafka/MQ에 저장
&rarr; Consumer가 처리 가능한 만큼 가져감
&rarr; 외부 발송 API 호출
&rarr; 성공/실패 상태 저장
</code></pre>
<p>이 구조의 장점은 다음과 같다.</p>
<p>첫째, 요청이 몰려도 큐가 중간에서 받아준다.<br />둘째, 처리 속도를 조절할 수 있다.<br />셋째, 발송 로직과 요청 로직을 분리할 수 있다.<br />넷째, 실패한 메시지를 재처리하기 쉽다.</p>
<p>쉽게 말하면 큐는 카페의 주문표와 비슷하다.<br />손님이 한 번에 많이 와도 직원이 주문표를 받아두고, 커피는 만들 수 있는 속도에 맞춰 하나씩 만든다.<br />Kafka나 MQ도 이와 비슷하게 요청을 먼저 받아두고, 처리 가능한 속도로 뒤에서 처리하게 해준다.</p>
<h2>3. Consumer란 무엇인가</h2>
<p>Consumer는 큐에 쌓인 메시지를 꺼내서 실제 작업을 처리하는 쪽이다.</p>
<pre class="makefile"><code>Kafka/MQ = 주문표가 쌓이는 곳
Consumer = 주문표를 보고 실제 작업을 처리하는 작업자
</code></pre>
<p>예를 들어 이메일 발송 시스템에서는 Consumer가 Kafka에서 발송 메시지를 읽고, 외부 이메일 API를 호출한 뒤 결과를 DB에 저장한다.</p>
<p>Consumer 수를 늘리면 동시에 처리하는 작업자 수가 늘어나므로 처리량이 증가할 수 있다.<br />하지만 Consumer를 무조건 많이 늘리면 DB나 외부 API에 부담이 갈 수 있다.<br />따라서 Consumer 수는 DB 커넥션 풀, 외부 API 처리 한도, 평균 응답 시간 등을 고려해서 정해야 한다.</p>
<h2>4. DLQ란 무엇인가</h2>
<p>DLQ는 Dead Letter Queue의 약자로, 계속 처리에 실패한 메시지를 따로 보관하는 실패 큐다.</p>
<p>예를 들어 이메일 발송 메시지가 있다고 하자.</p>
<pre class="armasm"><code>이메일 발송 요청 A
이메일 발송 요청 B
이메일 발송 요청 C
</code></pre>
<p>이 중 B가 계속 실패할 수 있다.</p>
<pre class="angelscript"><code>B 1차 발송 실패
B 2차 재시도 실패
B 3차 재시도 실패
</code></pre>
<p>이 메시지를 계속 일반 큐에 두면 다른 정상 메시지 처리에도 방해가 될 수 있다.<br />그래서 일정 횟수 이상 실패한 메시지는 별도 큐로 옮긴다.</p>
<pre class="angelscript"><code>3번 실패한 메시지
&rarr; 일반 큐에서 제외
&rarr; DLQ에 보관
&rarr; 운영자가 원인 확인 후 재처리 또는 실패 확정
</code></pre>
<p>DLQ는 Java 자체 기능이 아니라 Kafka, RabbitMQ, AWS SQS, IBM MQ 같은 메시지 큐 시스템에서 사용하는 개념이다.</p>
<p>실무에서는 DLQ를 직접 운영하지 않더라도 DB로 비슷한 처리를 하기도 한다.</p>
<pre class="angelscript"><code>발송 상태 = FAIL
재시도 횟수 = 3
오류 메시지 = API timeout
</code></pre>
<p>즉, 별도 DLQ가 없더라도 실패 상태, 오류 메시지, 재시도 횟수를 DB에 남기면 운영자가 실패 건을 확인하고 재처리할 수 있다.</p>
<h2>5. 멱등성이란 무엇인가</h2>
<p>멱등성은 같은 요청이 여러 번 들어와도 결과가 한 번 처리된 것과 같도록 만드는 것이다.</p>
<p>이메일 발송을 예로 들면, 같은 발송 요청이 두 번 처리되더라도 실제 이메일은 한 번만 발송되어야 한다.</p>
<p>왜 같은 요청이 두 번 들어올까?</p>
<pre class="angelscript"><code>1. Consumer가 메시지를 읽음
2. 이메일 발송은 성공함
3. 그런데 처리 완료 표시 전에 서버가 죽음
4. 큐 입장에서는 처리 완료 여부를 모름
5. 같은 메시지를 다시 전달함
6. 이메일이 중복 발송될 위험이 생김
</code></pre>
<p>이런 상황 때문에 멱등성 처리가 필요하다.</p>
<p>가장 일반적인 방법은 요청을 구분할 수 있는 고유 키를 사용하는 것이다.</p>
<pre class="angelscript"><code>sendRequestId = EMAIL-20260612-00001
</code></pre>
<p>처리 흐름은 다음과 같다.</p>
<pre class="angelscript"><code>1. 발송 요청 수신
2. sendRequestId로 이미 처리된 요청인지 확인
3. 처리된 적이 없으면 발송
4. 발송 성공 후 처리 완료 상태 저장
5. 같은 sendRequestId가 다시 오면 발송하지 않고 skip
</code></pre>
<p>DB를 사용한다면 발송 이력 테이블에 유니크 키를 걸 수 있다.</p>
<pre class="n1ql"><code>CREATE UNIQUE INDEX UK_SEND_REQUEST
ON SEND_HISTORY (SEND_REQUEST_ID);
</code></pre>
<p>Redis를 사용한다면 다음과 같은 키를 둘 수 있다.</p>
<pre class="angelscript"><code>processed:email:EMAIL-20260612-00001 = DONE
</code></pre>
<p>Redis에서는 SETNX를 활용할 수도 있다.<br />SETNX는 키가 없을 때만 저장하는 방식이다.</p>
<pre class="sas"><code>첫 번째 요청: key 없음 &rarr; 저장 성공 &rarr; 처리 진행
두 번째 요청: key 이미 있음 &rarr; 중복 요청으로 판단 &rarr; skip
</code></pre>
<p>다만 Redis는 TTL이나 장애 상황을 고려해야 한다.<br />중요한 발송 이력은 Redis만 믿기보다는 DB에도 최종 성공/실패 상태를 남기는 것이 안전하다.</p>
<h2>6. 멀티스레드란 무엇인가</h2>
<p>멀티스레드는 하나의 프로그램 안에서 여러 작업을 동시에 나눠 처리하는 방식이다.</p>
<p>예를 들어 발송 데이터 1,000건을 단일 스레드로 처리하면 다음과 같다.</p>
<pre class="angelscript"><code>1번 발송
2번 발송
3번 발송
...
1000번 발송
</code></pre>
<p>멀티스레드를 사용하면 여러 스레드가 작업을 나눠 처리할 수 있다.</p>
<pre class="angelscript"><code>스레드 1 &rarr; 1~200번 발송
스레드 2 &rarr; 201~400번 발송
스레드 3 &rarr; 401~600번 발송
스레드 4 &rarr; 601~800번 발송
스레드 5 &rarr; 801~1000번 발송
</code></pre>
<p>대량 발송처럼 반복 작업이 많은 경우 멀티스레드는 처리 속도를 높이는 데 도움이 될 수 있다.</p>
<p>하지만 멀티스레드를 사용한다고 항상 성능이 좋아지는 것은 아니다.<br />스레드가 너무 많으면 오히려 문제가 생길 수 있다.</p>
<h2>7. 컨텍스트 스위칭이란 무엇인가</h2>
<p>컨텍스트 스위칭은 CPU가 여러 스레드를 번갈아 실행하기 위해 현재 작업 상태를 저장하고 다른 작업 상태를 불러오는 과정이다.</p>
<p>예를 들어 CPU가 스레드 A를 처리하다가 스레드 B로 넘어가야 한다면 다음 과정이 필요하다.</p>
<pre class="armasm"><code>스레드 A 상태 저장
&rarr; 스레드 B 상태 불러오기
&rarr; 스레드 B 실행
</code></pre>
<p>이 전환 과정 자체에도 비용이 든다.</p>
<p>사람으로 비유하면, 개발하다가 메일 답장하고, 다시 개발하다가 전화 받고, 다시 회의록을 작성하는 것과 비슷하다.<br />일을 바꿀 때마다 이전 맥락을 다시 떠올려야 하므로 전환 비용이 생긴다.</p>
<p>스레드가 너무 많으면 실제 작업보다 스레드를 바꿔 끼우는 비용이 커질 수 있다.<br />그래서 멀티스레드는 무조건 많이 만드는 것이 아니라 적절한 수로 조정해야 한다.</p>
<h2>8. 멀티스레드에서 고려해야 할 자원</h2>
<p>대량 발송 시스템에서 스레드 수를 정할 때는 내 서버만 보면 안 된다.</p>
<p>다음 요소를 함께 고려해야 한다.</p>
<pre class="x86asm"><code>CPU
메모리
DB 커넥션 풀
외부 API 처리 한도
네트워크
평균 응답 시간
타임아웃
재시도 정책
</code></pre>
<p>예를 들어 스레드를 100개 만들었는데 DB 커넥션 풀이 10개라면, 동시에 DB 작업을 할 수 있는 요청은 10개뿐이다.<br />나머지 90개는 커넥션이 반환될 때까지 기다려야 한다.</p>
<p>또 외부 발송 업체가 초당 50건만 처리할 수 있는데 내 서버가 초당 500건을 보내면, 외부 업체에서 요청 초과나 timeout이 발생할 수 있다.</p>
<p>따라서 스레드 수는 단순히 크게 잡는 것이 아니라 하위 자원이 감당할 수 있는 수준으로 정해야 한다.</p>
<h2>9. API Rate Limit이란 무엇인가</h2>
<p>API Rate Limit은 외부 API가 일정 시간 동안 받을 수 있는 요청 수 제한이다.</p>
<p>예를 들어 외부 이메일 업체가 다음과 같이 제한할 수 있다.</p>
<pre class="angelscript"><code>초당 100건 요청 가능
분당 3,000건 요청 가능
동시 연결 20개까지 가능
</code></pre>
<p>이 한도를 넘으면 다음과 같은 문제가 발생할 수 있다.</p>
<pre class="pf"><code>429 Too Many Requests
Rate limit exceeded
timeout
일시적 요청 실패
</code></pre>
<p>따라서 대량 발송 시스템에서 스레드 수를 늘릴 때는 외부 업체의 처리 한도도 반드시 확인해야 한다.</p>
<h2>10. DB 커넥션 풀과 트랜잭션 범위</h2>
<p>DB 커넥션 풀은 애플리케이션이 DB와 연결할 수 있도록 미리 만들어둔 연결 묶음이다.<br />Spring Boot에서는 HikariCP를 많이 사용한다.</p>
<p>예를 들어 커넥션 풀 최대 개수가 50이라면 동시에 DB 작업에 사용할 수 있는 커넥션은 최대 50개다.</p>
<pre class="angelscript"><code>동시 요청 200개
DB 커넥션 최대 50개
&rarr; 50개는 DB 작업
&rarr; 150개는 커넥션 반납 대기
</code></pre>
<p>커넥션을 오래 잡고 있으면 다른 요청들이 기다리게 된다.</p>
<p>특히 @Transactional 범위가 너무 넓으면 문제가 될 수 있다.</p>
<pre class="less"><code>@Transactional
public void process() {
    saveData();          // DB 작업
    callExternalApi();   // 외부 API 호출
    sendEmail();         // 이메일 발송
    updateStatus();      // DB 작업
}
</code></pre>
<p>이 경우 외부 API 호출이나 이메일 발송 중에도 트랜잭션이 유지될 수 있고, DB 커넥션 반납이 늦어질 수 있다.</p>
<p>개선 방향은 트랜잭션 안에는 꼭 필요한 DB 작업만 두고, 외부 API 호출이나 이메일 발송은 트랜잭션 밖으로 분리하는 것이다.</p>
<pre class="cpp"><code>public void process() {
    saveDataInTransaction();  // DB 작업만 짧게 처리
    sendEmailAsync();         // 이메일 발송은 비동기 처리
}
</code></pre>
<h2>11. DB 커넥션 풀은 늘리면 해결될까</h2>
<p>DB 커넥션 풀은 Spring 설정으로 늘릴 수 있다.</p>
<pre class="yaml"><code>spring:
  datasource:
    hikari:
      maximum-pool-size: 100
</code></pre>
<p>하지만 무작정 늘리는 것은 위험하다.</p>
<p>DB 커넥션은 한정된 자원이다.<br />커넥션이 많아지면 DB 서버의 메모리, CPU, 세션 관리 비용, 락 경합, 디스크 I/O 부담이 증가할 수 있다.</p>
<p>따라서 커넥션 풀을 늘리기 전에 먼저 확인해야 할 것이 있다.</p>
<pre class=""><code>트랜잭션 범위가 너무 길지 않은지
느린 쿼리가 있는지
외부 API 호출을 트랜잭션 안에서 하고 있지 않은지
커넥션이 제대로 반납되고 있는지
커넥션 누수가 없는지
요청을 큐로 완충할 수 있는지
</code></pre>

<h2>12. 정리</h2>
<p>대량 처리 시스템에서는 단순히 스레드 수를 늘리거나 서버 성능을 높이는 것만으로는 안정적인 처리가 어렵다.</p>
<p>동기 처리는 단순하지만 오래 걸리는 작업이 전체 응답을 지연시킬 수 있다.<br />비동기 처리는 오래 걸리는 작업을 분리해 사용자 응답과 실제 처리를 나눌 수 있다.<br />메시지 큐는 요청이 몰렸을 때 중간에서 완충 역할을 한다.<br />DLQ는 계속 실패하는 메시지를 따로 보관하는 실패 큐다.<br />멱등성은 같은 요청이 여러 번 들어와도 한 번만 처리되도록 보장하는 방식이다.<br />멀티스레드는 처리량을 높일 수 있지만, DB 커넥션 풀이나 외부 API 처리 한도 같은 하위 자원이 감당할 수 있어야 한다.<br />DB 커넥션 풀은 늘릴 수 있지만, 무작정 늘리기보다 트랜잭션 범위와 쿼리 성능, 외부 API 호출 위치를 먼저 점검해야 한다.</p>
<p>결국 중요한 것은 &ldquo;얼마나 많이 동시에 처리할 것인가&rdquo;보다 &ldquo;각 자원이 감당할 수 있는 만큼 안정적으로 처리하는 구조를 만드는 것&rdquo;이다.</p>
