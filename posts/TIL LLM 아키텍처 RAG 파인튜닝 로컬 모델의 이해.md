<h2>1. RAG vs 파인튜닝(Fine-Tuning): 목적이 완전히 다르다</h2>
<p>둘의 개념을 처음 받아들였을 때 둘 다 AI교육을 하는건데 구분을 하기가 헷갈렸다.&nbsp;</p>
<ul>
<li><b>RAG (검색 증강 생성): "외부 DB 조회 (오픈북 테스트)"</b>
<ul>
<li><b>개념:</b> 질문이 들어오면 사내 DB나 문서를 먼저 검색한 뒤, 그 내용을 프롬프트에 끼워 넣어 대답하게 하는 방식이다.</li>
<li><b>특징:</b> 지식이 바뀔 때마다 데이터베이스나 데이터셋을 새로운 정보로 업데이트하기만 하면 된다. 출처 확인이 가능해 신뢰도가 높고 환각(거짓말)을 줄일 수 있다.</li>
<li><b>깨달음:</b> "최신 팩트와 정보"가 필요하다면 무조건 RAG를 써야 한다.</li>
<li><b>실생활 활용 사례</b>
<ul>
<li><b>고객 지원 챗봇 (FAQ):</b> 특정 분야 내의 질답(FAQ)을 처리할 때 주로 사용</li>
<li><b>사내 규정 및 매뉴얼 검색:</b> "올해 바뀐 연차 수당 계산법 알려줘"처럼 정보가 자주 바뀌는 사내 인트라넷 환경에서 활용</li>
<li><b>대규모 콘서트 티켓팅 시스템의 AI 어시스턴트 (예시):</b> 사용자가 "이번 크리스마스 콘서트 VIP석 예매 취소 수수료가 얼마야?"라고 물었을 때, AI가 혼자 지어내지 않고 DB에 있는 최신 환불 규정을 즉시 검색해서 대답하게 함</li>
</ul>
</li>
</ul>
</li>
<li><b>파인튜닝 (미세조정): "프레임워크 자체의 체질 개선"</b>
<ul>
<li><b>개념:</b> 방대한 데이터를 주입해 모델의 내부 가중치(뇌 구조) 자체를 특정 도메인에 맞게 아예 뜯어고치는 재학습 과정이다.</li>
<li><b>특징:</b> 모델을 특정 작업이나 도메인에 맞게 최적화하여 효율성을 높인다. 대신 파인 튜닝 과정이 자원을 많이 소모하며 시간이 많이 걸리고, 지식이 바뀌면 다시 트레이닝해야 한다.</li>
<li><b>깨달음:</b> AI가 특정 말투를 쓰게 하거나, 결과를 무조건 '특정 JSON 포맷'으로만 출력하도록 모델의 '행동 양식'을 고정해야 할 때 쓴다.</li>
<li><b>실생활 활용 사례</b>
<ul>
<li><b>특수한 아웃풋 포맷 강제:</b> 모델이 특정한 형식을 따르도록 만들 때 탁월합니다. 예를 들어, 고객의 장황한 컴플레인 메일을 읽고 시스템이 처리할 수 있는 완벽한 JSON 형식({"intent": "refund", "ticket_id": "12345"})으로만 출력하도록 훈련. 이 JSON 데이터를 <b>Kafka</b> 같은 메시지 큐에 던져 비동기로 환불 로직을 처리하게 한다.</li>
<li><b>텍스트 감정 분석 및 전문 용어 내재화:</b> 의료, 과학, 보험 등 그 분야 내 고유의 언어가 있는 환경에서 전문성을 올릴 때 사용.</li>
</ul>
</li>
</ul>
</li>
</ul>
<p>  <b>나의 착각 포인트:</b> ChatGPT에서 만드는 'Custom GPT(나만의 GPT)'에 문서를 업로드하는 것은 파인튜닝이 아니라 <b>고도화된 RAG + 프롬프트 엔지니어링</b>이다! 진짜 파인튜닝은 JSONL 데이터셋을 서버에 올려 모델을 새로 컴파일하는 수준의 작업이다.</p>
<h2>2. LLM 디자인의 기본: 느리고 비싼 API 다루기</h2>
<p>LLM은 일반적인 프로그래밍 로직과 다르다. 이 사실을 인지하고 시스템을 설계해야 한다.</p>
<ul>
<li><b>LLM 사용 최소화:</b> 결정론적 코드는 이해하고 유지 관리하기 쉽고 테스트하기 쉽다. 따라서 일반 코드로 해결 가능한 것(예: 단순 텍스트 추출)은 코드로 짜고, 진짜 자연어 이해가 필요한 곳에만 LLM을 써야 비용과 속도를 잡을 수 있다.</li>
<li><b>확장성과 안정성 고려:</b> 상용 서비스로 제공하려면 확장성과 안정성 필수로 고려해야 한다. 외부 API를 동기(Sync)로 통신하면 시스템이 뻗을 수 있다. 반드시 비동기 큐(Message Queue)나 캐시(Redis)를 도입해 백엔드 아키텍처를 방어해야 한다.</li>
<li><b>보안 문제 (Data goes to OpenAI):</b> 단순 API 호출 시, 유저의 민감한 데이터(예: 피검사 결과 등)가 외부망을 타고 OpenAI 서버로 전송되는 심각한 보안 문제가 발생할 수 있다.</li>
</ul>
<h2>3. 로컬 LLM과 경량화 기술: 내 컴퓨터에서 AI 돌리기</h2>
<p>보안(망분리) 문제와 비용 문제를 한 번에 해결하는 방법은 **'오픈소스 모델을 내 로컬 서버에 띄우는 것'**이다. 이를 가능하게 하는 핵심 기술들을 배웠다.</p>
<ul>
<li><b>Ollama (올라마):</b> 메타의 Llama 3 같은 오픈소스 모델을 내 컴퓨터에서 클릭 한 번에 띄워주는 도구다. 비유하자면 'LLM을 위한 Docker'와 같다. 완벽한 오프라인 환경(심지어 비행기 안)에서도 내 코드를 분석하고 리뷰해 주는 AI를 무료로 쓸 수 있다.</li>
<li><b>양자화 (Quantization):</b> "왜 파일 크기를 줄이는데 정확도가 떨어질까?" 궁금했는데, 백엔드의 데이터 타입 캐스팅(Casting)과 같은 원리였다. 가중치의 정밀도를 감소하여 메모리 사용량을 줄이는 기술이다. 정밀한 소수점(float32)을 덜 정밀한 정수(int8 등)로 뭉뚱그려(양자화) 저장하기 때문에, 모델 크기는 1/4로 줄지만 약간의 오차(정확도 하락)가 발생하게 된다.</li>
<li><b>LoRA &amp; QLoRA:</b> 무식하게 전체 모델을 재학습하는 게 아니라, 사전 학습된 모델의 가중치를 고정하고 각 계층에 작은 훈련 가능한 매개변수 세트를 주입(어댑터 연결)하여 파인튜닝하는 가성비 최강의 기법이다. QLoRA는 여기에 모델 가중치를 양자화하여 더욱 효율을 극대화한 방법이다.</li>
</ul>
